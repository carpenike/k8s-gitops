# Kata Containers for a VM-sandboxed workload

## Context and Problem Statement

A Hermes agent pilot needs to run as pods that are not `runc` on the
host. The nodes are Talos v1.14.5. The CNI is Cilium with kube-proxy
replacement. Socket-level load balancing in the pod cgroup does not
work inside a Kata VM, which is a separate Cilium change.

## Decision Drivers

- The runtime has to come from the Talos image. Talos has no package
  manager, and a privileged DaemonSet that installs a VMM fights the
  image model
- The pilot selects the QEMU hypervisor (`kata-qemu`)
- All four sleds should be able to run the sandbox
- Flux should own the `RuntimeClass` objects. It should not own a test
  pod

## Considered Options

- `siderolabs/kata-containers` on the Image Factory schematic, with
  RuntimeClasses for the handlers that extension registers
- gVisor (`siderolabs/gvisor`)
- A Kata install DaemonSet on an otherwise stock schematic

## Decision Outcome

Chosen option: "`siderolabs/kata-containers` on the Image Factory
schematic", because Image Factory lists that extension for Talos
v1.14.5 and the v1.14.5 extension README registers the containerd
handlers this pilot needs.

The schematic keeps `siderolabs/intel-ucode` and `siderolabs/nut-client`
and adds `siderolabs/kata-containers`. The id returned by
`POST https://factory.talos.dev/schematics` on 3 Nov 2026 is
`546ddf49f4f92f44c15fbeff45e07c984cf7626a2d5d080fb14d0727ecf78ba4`.
`topf.yaml` pins that id on every sled. The catalog entry observed
the same day is `ghcr.io/siderolabs/kata-containers:3.32.0`.

The extension registers two handlers:

| RuntimeClass | handler | hypervisor |
| --- | --- | --- |
| `kata` | `kata` | Cloud Hypervisor |
| `kata-qemu` | `kata-qemu` | QEMU |

The pilot uses `runtimeClassName: kata-qemu`. Overhead is the figure
in the extension README (`160Mi` memory and `250m` cpu for QEMU,
`130Mi` and `250m` for Cloud Hypervisor).

### Consequences

- Good, because a pod opts in with `runtimeClassName` and every sled
  has the same image once it has been upgraded
- Bad, because tuppr chart 0.5.10 does not roll a schematic change.
  `TalosUpgrade` runs when the Talos version changes, and it keeps the
  schematic the node is already running. Each sled needs
  `talosctl upgrade` to
  `factory.talos.dev/metal-installer/546ddf49f4f92f44c15fbeff45e07c984cf7626a2d5d080fb14d0727ecf78ba4:v1.14.5`.
  That upgrade reboots the node
- Bad, because `topf apply` only rewrites `machine.install.image`.
  Until the upgrade, the install image and the running schematic
  disagree, and tuppr's next version roll refuses that node
- The Cloud Hypervisor class is registered for the same extension.
  The pilot does not have to use it

## Pros and Cons of the Options

### Image Factory kata-containers extension

- Good, because the handler names match containerd config shipped by
  the extension
- Good, because intel-ucode and nut-client stay on the image
- Bad, because the extension is installed by a reboot, not by Flux

### gVisor

- Good, because it is also an official Talos extension
- Bad, because the pilot asked for a Kata QEMU sandbox, not gVisor

### Install DaemonSet

- Good, because it would not reboot the node to add a binary
- Bad, because it leaves the VMM off the immutable image and out of
  the schematic id tuppr and `talosctl upgrade` already understand
