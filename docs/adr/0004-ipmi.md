# Out-of-band management via IPMI/Redfish on Forge

## Context and Problem Statement

Four sleds in one chassis need temperatures, fan speeds, PSU status, and
the hardware event log watched while the cluster is up, and still watched
when it is not. After a UPS shutdown, something that is not a sled has to
power the machines back on in order once the battery has recovered. The
BMCs are on their own network and their credentials are a secret.

## Decision Drivers

- Hardware telemetry has to survive the cluster being down
- Alerts already terminate on Forge's Alertmanager
- The management network stays isolated from the node LAN
- BMC credentials stay in 1Password
- Four known machines do not need a provisioning control plane

## Considered Options

- prometheus `ipmi_exporter` on Forge, alerts to Forge's Alertmanager
- The same exporter installed in the cluster
- Omni, or Sidero Metal, for bare-metal PXE provisioning

## Decision Outcome

Chosen option: "prometheus `ipmi_exporter` on Forge", because Forge is the
host that is still up when the sleds are powered off, and it already runs
Alertmanager. The exporter scrapes each BMC for temperatures, fans, PSU
status, and the hardware event log. This repository documents the
placeholder addresses and the power order. The exporter, the scrape
config, and the real management subnet live in the Forge NixOS repo.

An in-cluster `ipmi_exporter` is not installed. It would need a route from
pod CIDRs onto the management network, and it would go silent in the same
outage it is meant to explain.

Omni and Sidero Metal are rejected. Both exist to PXE-boot and enroll
machines through a provisioning plane. These four sleds are installed from
the Image Factory with `topf`. A second control plane, a PXE DHCP service,
and a machine API are more moving parts than the cluster.

Power-on after the battery recovers is also Forge, over IPMI or Redfish,
in the order in `docs/architecture.md`: control planes `sled-0`, `sled-1`,
`sled-2`, then the worker `sled-3`. Shutdown is the NUT primary, in the
reverse order. The Talos `nut-client` patch is identical on every sled.

`cluster.example.toml` uses RFC 5737 TEST-NET-2 (`198.51.100.0/24`) for
the management network. The 1Password item name is `PLACEHOLDER_ITEM_BMC`.

### Consequences

- Good, because a dead cluster still has BMC metrics and a way back on
- Good, because the management network never has to be reachable from pods
- Bad, because the scrape config and the power script are in another repo,
  and this one can only record the order and the placeholders

## Pros and Cons of the Options

### ipmi_exporter on Forge

- Good, because it keeps working while the sleds are off, and the alerts
  join the existing Forge Alertmanager
- Bad, because the NixOS config is not reviewed in this pull request

### In-cluster ipmi_exporter

- Good, because the scrape config would sit next to the other manifests
- Bad, because it couples BMC reachability to the cluster, and it is down
  during the outage that power sequencing has to handle

### Omni or Sidero Metal

- Good, because PXE enrollment is the right tool for a fleet that is
  rebuilt often or that is too large to image by hand
- Bad, because four sleds with a known Image Factory schematic do not need
  that fleet, and the extra DHCP and API surface would sit on the
  management network next to the BMCs
